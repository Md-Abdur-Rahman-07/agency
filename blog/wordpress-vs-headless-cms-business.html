WordPress or a Headless CMS? Choose Around Your Editors

On this page

  2. Understand what separation changes
  3. Compare a normal publishing day
  4. Look at total operating responsibility
  5. Choose with a short proof of concept

The short answer

Choose the publishing workflow first. A separate frontend is useful when it solves a real delivery requirement, but it adds systems that someone must maintain.

The person updating your website every week should have a voice in how it is built. A platform can look excellent in a technology comparison and still make a routine content change unnecessarily difficult. Start by asking an editor to show how a page moves from draft to publication today.

WordPress and a headless CMS are not perfectly opposing categories. WordPress can manage content in a conventional site or provide content to a separate frontend. The decision is about the architecture and working process, not just the name of the software.

Describe the content workflow

List the people who create, review and publish content. Include previews, scheduled publishing, media selection and corrections after launch. If a nontechnical team needs to see a draft exactly as customers will see it, make that an acceptance requirement rather than assuming every setup provides it automatically.

Try a representative task during evaluation: create a service page, add a photograph, link it from navigation and preview it on a phone. Record where a developer is required. That exercise often reveals more than comparing the number of features on a vendor's marketing page.

Understand what separation changes

The WordPress REST API exposes content through structured endpoints so other applications can interact with it. This makes it possible to use WordPress as a content source for a separate interface. The API is a capability, not a guarantee that every existing plugin will work unchanged in a different frontend. [1]

Ask how previews, forms, search, redirects and metadata will be delivered. With a conventional setup, some responsibilities may be handled within one installation. With separate systems, those responsibilities need explicit owners and connections. Neither approach removes the need for thoughtful implementation.

Compare a normal publishing day

  • Can an editor preview unpublished content without exposing it publicly?
  • Which changes can be made safely without a developer?
  • How do reusable blocks or content types prevent inconsistent pages?
  • What happens when a published item is renamed, removed or scheduled?
  • How quickly does a content change appear on the public site?
  • Who diagnoses a problem when the editor and public site show different versions?

Use real content in the comparison. A flexible editor can be helpful, but unlimited layout choices may also make consistency harder. Decide which parts of a page should be controlled by the design system and which need editorial freedom.

Look at total operating responsibility

Budget for hosting, updates, integration maintenance, training and support. A separate frontend may be appropriate for multiple channels or a highly customised application, but the team still needs to maintain the content system and its delivery path. Ask what happens if a build fails or an API becomes unavailable.

Do not assume that one architecture automatically ranks better. Clear content, crawlable pages, metadata, performance and reliable publishing all depend on implementation. Request evidence about the proposed site rather than treating a framework name as an SEO outcome.

Choose with a short proof of concept

Build one representative content type and complete its publishing workflow. Include a correction and a rollback, not just the first successful publish. Let the people who will use the system try it and describe what felt difficult.

The best choice is the one your team can operate while meeting the product's actual requirements. If those requirements are straightforward, avoid adding architectural separation without a clear benefit. If they are complex, document the reason for each extra component so the next maintainer understands the design.
