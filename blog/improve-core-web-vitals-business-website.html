How to Improve Core Web Vitals on a Business Website

15 November 20263 min read

On this page

  1. Establish a baseline you can repeat
  2. Find what delays the main content
  3. Give media a delivery budget
  4. Review every extra script
  5. Make performance part of acceptance
Explore Web Development ↗
The short answer

Start with a slow page that matters to the business, identify what delays its main content, then measure the same journey after each change.

A performance report can produce a long list of warnings. That does not mean every warning deserves the same budget. If the service page people visit from search is slow, improving that journey may be more useful than chasing a perfect score on a page almost nobody opens.

Begin with one representative page and a clear problem. Does useful content arrive late? Does the menu react slowly? Does the page jump while someone tries to tap a button? These are different experiences and may have different causes. A plan that simply says “optimise everything” makes it difficult to decide whether the work helped.

Establish a baseline you can repeat

Record the URL, device conditions, test method and date. Test several times and keep the results instead of choosing the best run. Where real-user data is available, compare it with controlled tests. A developer's fast laptop is not the same environment as a customer's phone on a variable connection.

Choose a small group of important templates: homepage, service page, article, product page or booking screen. A shared component can affect many pages, but one good result does not establish that every template performs well. Record the specific business task beside each page so performance work stays connected to use.

Find what delays the main content

Google's LCP optimisation guidance breaks the loading experience into parts, including server response, resource discovery and loading, and the delay before rendering. It recommends making an important image discoverable early and avoiding lazy loading for the LCP image. That helps identify the bottleneck rather than treating every slow page as a hosting problem. [1]

Ask your developer to show the request sequence for the page. If the main image starts downloading late, reducing its file size may help but will not explain why the browser discovered it late. If content is waiting for a script, buying a larger image server is unlikely to address the whole issue.

Give media a delivery budget

For each image, decide how large it appears and whether it needs to load immediately. Use suitable file sizes and dimensions, reserve layout space and review what gets sent to smaller screens. A full-resolution photograph from a camera is usually more than a card thumbnail needs.

Apply the same thinking to video. A background clip should earn its download cost. Consider a poster image and deliberate playback, especially when the clip is decorative. Keep the information a visitor needs available even when media fails or takes time to arrive.

Review every extra script

  • List analytics, chat, advertising, scheduling and embedded media tools.
  • Name the business owner and purpose of each tool.
  • Check whether the tool is needed on every page or only in one workflow.
  • Test customer tasks after removing or changing a script.
  • Keep a record of the trade-off rather than reinstalling everything later.

Do not remove measurement or support tools blindly. Agree which capabilities are essential and which could load later. The useful discussion is about timing and value, not a competition to produce the smallest possible script count.

Make performance part of acceptance

Repeat the original tests after the change and check forms, navigation and purchases as well. A faster page that loses the enquiry is not an improvement. Include representative content in the test: empty templates can hide the cost of real images and integrations.

Keep the baseline with the project handover. When a new campaign widget or video arrives, the team can compare its impact. Performance becomes easier to maintain when it is a continuing constraint rather than a one-off score delivered at launch.
